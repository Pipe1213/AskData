# Evaluation: can a non-expert trust AskData's answer?

AskData's users can't read SQL, so the worst failure is a **confident wrong answer**: a clean table and a sentence that look right and aren't. This eval measures that, together with the two behaviours meant to prevent it: asking when a question is unclear, and declining when the data can't answer.

## The questions

52 questions, 26 for each demo database (Pagila and `retail_ops`), in [`questions.json`](questions.json).

| Kind | dev / held-out | Expected behaviour |
|---|---|---|
| `answerable` | 16 / 20 | Correct result (checked against saved gold results) |
| `schema_lookup` | 2 / 0 | Names the right table |
| `ambiguous` | 2 / 6 | Ask a clarifying question (or answer one valid reading and say which) |
| `unanswerable` | 0 / 6 | Say the data can't answer it, and why |

Some questions are follow-ups ("Now show only the top 5") and are sent with the previous question as conversation context.

### dev and held-out

- **dev** (20) are the questions that existed before the eval was built; they were used while developing AskData.
- **held-out** (32) were written on 12 Oct 2026, before any run, and were never used to change prompts, retrieval or rules. When changing the system, only dev questions and dev failures were looked at.
- Held-out is the number to trust. If held-out questions are ever used for tuning, new ones must be written and the README must say so.

## Metrics

**Headline: silent-error rate** = questions where AskData returned an answer that is wrong (`wrong`) or answered something the data can't support (`fabricated`), divided by all questions. A clarifying question, a refusal or a visible error is not silent.

Also reported: answerable accuracy (`answerable` + `schema_lookup` correct), ambiguous questions clarified, unanswerable questions declined, latency (median, p90) and cost per question.

### Outcomes per question

| Kind | Response | Outcome |
|---|---|---|
| answerable | answer, matches gold | `correct` |
| answerable | answer, doesn't match | `wrong` (silent error) |
| answerable | clarification | `unneeded_clarification` |
| any | cannot_answer on an answerable/ambiguous question | `false_refusal` |
| ambiguous | clarification | `clarified` |
| ambiguous | answer matching one interpretation, `assumptions` non-empty | `assumed_stated` |
| ambiguous | same, no assumptions | `assumed_silent` |
| ambiguous | answer matching no interpretation | `wrong` (silent error) |
| unanswerable | cannot_answer | `declined` |
| unanswerable | clarification | `clarified` (acceptable) |
| unanswerable | answer | `fabricated` (silent error) |
| any | HTTP error / pipeline error | `error` (visible failure, not silent) |

## Results

Two runs of all 52 questions on 27 Oct 2026, SQL model `gpt-6.1-sol` (reasoning effort `low`), summaries `gpt-6-luna` (reasoning off). Both runs gave the same outcome on every question.

| Split | Answerable correct | Ambiguous: clarified | Unanswerable: declined | Silent errors | Median latency | Cost / question |
|---|---|---|---|---|---|---|
| dev (20) | 16/18 | 2/2 | — | 2/20 (10%) | 8.9 s / 9.4 s | $0.0086 / $0.0062 |
| held-out (32) | 19/20 | 4/6 | 6/6 | 1/32 (3%) | 7.8 s / 8.3 s | $0.0064 / $0.0044 |
| all (52) | 35/38 | 6/8 | 6/6 | 3/52 (6%) | 8.3 s / 8.7 s | $0.0072 / $0.0051 |

Run 1 / run 2 where they differ. The other two held-out ambiguous questions: one `assumed_stated`, one `false_refusal` (the only false refusal). No unneeded clarifications or errors. All three silent errors are on `retail_ops`. Files: [`results/`](results/) (one line per question with the full response, plus a summary).

## How matching works (`score.py`)

- Gold results are saved in `expected.json` (generated by `build_expected.py`, read-only transaction, `timezone=UTC`, the Docker default). Scoring needs no database access.
- Each answerable question can have several accepted gold queries (`gold_sql` list) when there are several reasonable readings (e.g. revenue by order date or payment date). Any match counts.
- Column names are ignored. Each `match.required` group lists gold columns that identify a value (e.g. `["customer_id", "customer_name", "first_name"]`); one of them must appear among the predicted columns, found by value. Extra predicted columns are fine.
- Rows must line up: the matched columns are compared as row tuples.
- `ordered_column`: that column's sequence must match (rankings, trends).
- `prefix_ok`: a top-N slice of the gold ranking is accepted ("Which store had more…?" can return just the winner).
- Rows tied with the last value of a ranking are left out of the identity check (which tied rows appear is arbitrary).
- Numbers match within 0.011 absolute or 0.01% relative, so 2-decimal rounding passes. Midnight timestamps are reduced to dates. Text is compared case-insensitively.
- `expect_empty`: correct only when zero rows come back.
- Checked by `python eval/test_score.py`, plus realistic SQL run against the real data: separate first/last names ✓, `to_char` months ✓, winner-only ✓; one partition only ✗, cancelled orders counted as revenue ✗, wrong year ✗.

## Response contract the scorer reads

`POST /query` returns a `QueryResponse`. The scorer reads `response_type`, `columns`, `rows`, `assumptions`, `answer_summary`, `generated_sql` and `usage`:

```json
{
  "response_type": "answer | clarification | cannot_answer",
  "clarification": {"question": "“Best” can mean… Which one?", "options": ["Spent the most money", "Rented the most films"]},
  "cannot_answer": {"reason": "No cost data is recorded…", "alternatives": ["Which films earned the most revenue?"]},
  "assumptions": ["“spent” = total of all payments", "all dates (Jan – Jul 2022)"],
  "usage": {"llm_calls": 3, "input_tokens": 5120, "output_tokens": 410, "cost_usd": 0.0041}
}
```

For `clarification` and `cannot_answer`, `columns`/`rows` are empty and no SQL is run. A response without `response_type` counts as `answer`.

`usage` also carries `cached_input_tokens`, `reasoning_tokens` and `unpriced_models`, and is present on error responses too. `cost_usd` comes from the per-model price table in `backend/app/core/config.py` (OpenAI list prices, with the date they were checked) and is `null` when a model has no price there.

## Running it

Needs the backend running with the right dataset loaded (`make docker-up`, `make backend-dev`).

```bash
make load-dataset DATASET=pagila && make reload-schema-cache
python eval/score.py --dataset pagila --label mine
make load-dataset DATASET=retail_ops && make reload-schema-cache
python eval/score.py --dataset retail_ops --label mine
python eval/score.py --summarize eval/results/*_mine_*.jsonl
```

Results go to `eval/results/<time>_<label>_<dataset>.jsonl` and a `.summary.json`. `--rescore` re-scores saved responses after a matcher change, without calling the backend. `--split dev|heldout` runs one split. A full run of 52 questions costs about $0.25–0.40.

Regenerate gold results only if questions or seed data change:
```bash
python eval/build_expected.py --dataset pagila --dsn postgresql://postgres:postgres@localhost:55432/pagila
```

## Facts about the data that the questions rely on

- Pagila's `payment` is a **partitioned table** (`relkind = 'p'`) with 7 monthly partitions `payment_p2022_01…07`. Schema introspection must list the parent and hide the partitions, otherwise a model sums only some months. Pagila declares the payment foreign keys on the partitions, not on the parent, so AskData maps them to the parent. "Which 10 customers spent the most?": Karl Seal (526) 221.55, then Eleanor Hunt 216.54, Clara Shaw 195.58, Rhonda Kennedy and Marion Snyder tied at 194.61.
- Pagila dates: payments 23 Jan – 27 Jul 2022; rentals 14 Feb – 23 Aug 2022 (none in March–April). Monthly counts depend on timezone; gold uses UTC.
- retail_ops: orders 2023-01-01 – 2024-12-30; `payments.amount` equals order-item value net of discounts for every non-cancelled order; cancelled orders have no payment. Revenue = payments (counting cancelled orders is wrong). retail_ops has supplier `unit_cost`, so margin questions are answerable there but not in Pagila.
- Orders have both a store region and a customer region, and they give different totals: that's why "revenue by region" is ambiguous.
