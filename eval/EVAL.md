# Evaluation: can a non-expert trust AskData's answer?

Phase 1 of the AskData plan (done 12 Oct 2026).

## What is measured

AskData's users can't read SQL, so the worst failure is a **confident wrong answer**. The eval checks three behaviours, not just accuracy:

| Kind | Count (dev / held-out) | Expected behaviour |
|---|---|---|
| `answerable` | 16 / 20 | Correct result (checked against gold SQL results) |
| `schema_lookup` | 2 / 0 | Names the right table |
| `ambiguous` | 2 / 6 | Ask a clarifying question (or answer one valid reading and say which) |
| `unanswerable` | 0 / 6 | Say the data can't answer it, and why |

52 questions in total: 26 Pagila, 26 retail_ops.

**Headline metric: silent-error rate** = questions where AskData returned an answer that is wrong (`wrong`) or answered something the data can't support (`fabricated`), divided by all questions.

Other metrics: answerable accuracy, ambiguous clarified (and "handled" = clarified + answered with a stated assumption), unanswerable declined, latency median/p90, cost per question.

### Outcomes per question

| Kind | Response | Outcome |
|---|---|---|
| answerable | answer, matches gold | `correct` |
| answerable | answer, doesn't match | `wrong` (silent error) |
| answerable | clarification | `unneeded_clarification` |
| any | cannot_answer on an answerable/ambiguous question | `false_refusal` |
| ambiguous | clarification | `clarified` |
| ambiguous | answer matching one interpretation, `assumptions` non-empty | `assumed_stated` |
| ambiguous | same, no assumptions | `assumed_silent` |
| ambiguous | answer matching no interpretation | `wrong` (silent error) |
| unanswerable | cannot_answer | `declined` |
| unanswerable | clarification | `clarified` (acceptable) |
| unanswerable | answer | `fabricated` (silent error) |
| any | HTTP error / pipeline error | `error` (visible failure, not silent) |

## Splits: dev vs held-out (important)

- **dev** = the 20 questions that already existed in `demo_data/example_questions/*_benchmark.json`. The code was tuned on them (see `PagilaAdapter` in `backend/app/services/dataset_adapters.py` and the keyword lists in `planner_service.py`), so dev scores overstate quality.
- **held-out** = 32 new questions written on 12 Oct 2026 before any run.
- **Rule:** when changing prompts, planner rules, adapters or retrieval, look only at dev questions and dev failures. Don't read held-out questions or their failures to tune the system. Report held-out as the real number. If held-out questions are ever used for tuning, write new held-out questions and say so in the README.

## How matching works (`eval/score.py`)

- Gold results are saved in `eval/expected.json` (generated by `eval/build_expected.py`, read-only transaction, `timezone=UTC`, the Docker default). Scoring needs no DB access.
- Each answerable question can have several accepted gold queries (`gold_sql` list) when there are several reasonable readings (e.g. revenue by order date or payment date). Any match counts.
- Column names are ignored. Each `match.required` group lists gold columns that identify a value (e.g. `["customer_id", "customer_name", "first_name"]`); one of them must appear among the predicted columns, found by value. Extra predicted columns are fine.
- Rows must line up: the matched columns are compared as row tuples.
- `ordered_column`: that column's sequence must match (rankings, trends).
- `prefix_ok`: a top-N slice of the gold ranking is accepted ("Which store had more…?" can return just the winner).
- Rows tied with the last value of a ranking are left out of the identity check (which tied rows appear is arbitrary).
- Numbers match within 0.011 absolute or 0.01% relative, so 2-decimal rounding passes. Midnight timestamps are reduced to dates. Text is compared case-insensitively.
- `expect_empty`: correct only when zero rows come back.
- Checked: `python eval/test_score.py` (20 tests), plus realistic SQL run against the real data: separate first/last names ✓, `to_char` months ✓, winner-only ✓; one partition only ✗, cancelled orders counted as revenue ✗, wrong year ✗.

## Response contract the scorer reads

Current fields (`QueryResponse`): `columns`, `rows`, `row_count`, `answer_summary`, `generated_sql`, `used_tables`. With today's code every 200 response counts as `response_type = "answer"`.

**Fields to add in phase 2** (all optional, so old runs still score):

```json
{
  "response_type": "answer | clarification | cannot_answer",
  "clarification": {"question": "“Best” can mean… Which one?", "options": ["Spent the most money", "Rented the most films"]},
  "cannot_answer": {"reason": "No cost data is recorded…", "alternatives": ["Which films earned the most revenue?"]},
  "assumptions": ["“spent” = total of all payments", "all dates (Jan – Jul 2022)"],
  "usage": {"llm_calls": 3, "input_tokens": 5120, "output_tokens": 410, "cost_usd": 0.0041}
}
```

For `clarification` and `cannot_answer`, `columns`/`rows` are empty and no SQL is run.

## Running it

Needs the backend running with the right dataset loaded (`make docker-up`, `make backend-dev`).

```bash
make load-dataset DATASET=pagila && make reload-schema-cache
python eval/score.py --dataset pagila --label baseline
make load-dataset DATASET=retail_ops && make reload-schema-cache
python eval/score.py --dataset retail_ops --label baseline
python eval/score.py --summarize eval/results/*_baseline_*.jsonl
```

Results go to `eval/results/<time>_<label>_<dataset>.jsonl` (one line per question with the full response) and a `.summary.json`. `--rescore` re-scores saved responses after a matcher change, without calling the backend. `--split dev|heldout` runs one split.

Regenerate gold results only if questions or seed data change:
```bash
python eval/build_expected.py --dataset pagila --dsn postgresql://postgres:postgres@localhost:55432/pagila
```

## Known facts from building the set (12 Oct 2026)

- **The README demo answer is wrong.** "Which 10 customers spent the most in total?" was answered with Marion, $64.87. Correct: Karl Seal (526) $221.55, then Eleanor Hunt $216.54, Clara Shaw $195.58, Rhonda Kennedy and Marion Snyder tied at $194.61. Only 4 of the app's 10 names are in the real top 10.
- **Root cause:** `TABLES_QUERY` in `backend/app/db/introspection.py` keeps only `relkind = 'r'`. Pagila's `payment` is a partitioned table (`relkind = 'p'`), so it is invisible; only its 7 partitions `payment_p2022_01…07` (`relispartition = true`) are shown, and the model unions some of them. Fix: `cls.relkind IN ('r', 'p') AND NOT cls.relispartition` (and the same filter for columns/keys), then remove the `payment_p` special cases in `retrieval_service.py` and `dataset_adapters.py`.
- Pagila dates: payments 23 Jan – 27 Jul 2022; rentals 14 Feb – 23 Aug 2022 (none in March–April). Monthly counts depend on timezone; gold uses UTC.
- retail_ops: orders 2023-01-01 – 2024-12-30; `payments.amount` equals order-item value net of discounts for every non-cancelled order; cancelled orders have no payment. Revenue = payments (counting cancelled orders is wrong). retail_ops has supplier `unit_cost`, so margin questions are answerable there but not in Pagila.
- Orders have both a store region and a customer region, and they give different totals: that's why "revenue by region" is ambiguous.
